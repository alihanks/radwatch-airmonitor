## Weather parser: missing values as 0.0 vs NaN

**Where:** `image_scripts/weather_utils.py`, `parse_weather_data`.

**Current behavior:** empty cells and non-numeric placeholders (`--`, etc.) are mapped to `0.0`. Historical behavior since before this repo was versioned here.

**Why it matters:** `0.0` and "no reading" are not the same physical statement. A missing solar reading mapped to `0.0` looks like nighttime; a missing rain reading looks like no rain; missing wind speed looks calm. Aggregations and wind roses over these cells carry small biases.

**What a fix would look like:** map missing cells to `math.nan` instead of `0.0`, then audit each consumer downstream (`h5_analysis.py`, `weather_utils.draw_windrose`, rain accumulation logic) to ensure NaN is handled gracefully (e.g. masked from sums, skipped in histograms). Not a one-liner because the plotting code wasn't written with NaN safety in mind across every weather field.

## Pre-2018 spectral data: backwards-compatibility is unverified

**Where:** `current/` only — the pre-2018 CNFs live in the Dropbox `RPAVLOVSKY` folder and are not processed by any existing analysis.

**Observation:** the published pre-2018 numbers were generated by an older pipeline with different analysis procedures (e.g. ROI definitions, calibration, channel count) and live nowhere on the current server. The current pipeline is *intended* to be backwards-compatible — the CNF parser handles the older format — but nobody has actually run older CNFs through end-to-end and compared against the original published numbers.

**What a fix would look like:** pick a known pre-2018 date with a published result, pull those CNFs into a scratch directory, run `raw_analysis.py` + `h5_analysis.py` pointed at that directory, and check whether the numbers reproduce. If yes, document the invocation in the runbook. If no, diagnose the drift (likely calibration-era mismatch).

**Context:** the p75 baseline + 0.70 raw-drop threshold landed on 2026-04-21 and appear to resolve the observed edge dips. These thresholds were picked from first principles, not tuned against a sample of known-good vs known-bad spectra.

## `build_merged_weather` doesn't extend past the last radiation timestamp

**Where:** `image_scripts/analysis/h5_analysis.py`, `build_merged_weather()`.

**Current behavior:** the function starts with the radiation timestamps as the base timeline and only fills CSV weather points into *interior* gaps (`for i in range(1, len(rad_timestamps))`). CSV weather points that fall **after** the last radiation timestamp are silently dropped.

**Why it matters:** if the detector stops for any reason — even briefly — the weather subplots on `iso_*.png` won't show data for the trailing window between the last radiation sample and now, even though `weather_sorted.csv` has those entries. Surfaced as the "missing weather" symptom during the 2026-05-15 stale-marker incident: weather looked broken because radiation was stuck two weeks back, and the merged timeline couldn't reach past that.

**What a fix would look like:** after the interior-gap loop, append any CSV entries with `timestamp > rad_timestamps[-1]` to `merged_ts` / `merged_*`, then re-sort. Single-digit lines of code. Worth doing because it makes the weather subplots an honest "what we know" view independent of detector availability, and would have made the 2026-05-15 incident easier to spot (weather would have stayed current while radiation went stale, signaling clearly which pipeline was broken).

**Why deferred:** the immediate fix for the 2026-05-15 incident (date-dir regex tightening) restored radiation flow, so the symptom went away on its own. But the underlying tail-gap limitation in `build_merged_weather` remains, and will manifest again the next time radiation stops while the weather scraper keeps running.

## SRSO software-mitigation freeze workaround (pending observation)

**Where:** the dosenet server itself, not the repo. Documented in `docs/runbook.md` §7a.

**Status as of 2026-06-01:** the 2026-05 server freezes were diagnosed as the Linux/AMD SRSO Safe-RET soft-lockup bug on Zen 1 hardware. The microcode-update path (`maintenance/update_microcode.sh`) has been run and confirmed there is no further microcode AMD can deliver for this CPU (Ryzen 7 1700X = Zen 1; AMD published IBPB-extending microcode only for Zen 3/4). The remaining fix is the GRUB kernel parameter `spec_rstack_overflow=off`, documented in the runbook.

**Deferred because:** the user wants to observe whether the freezes recur over the next few days before applying the workaround. The maintenance script and runbook are in place so the change is one short edit + `update-grub` + reboot if needed.

**What a fix would look like:** the runbook §7a step 2 has the exact commands. The kernel param disables the software-only Safe-RET mitigation, which is the layer carrying the soft-lockup bug. Trade-off: the CPU then exposes SRSO to local attackers, which is acceptable for this single-purpose lab server.
